# Reflection

I drew the lines between the tools by asking what each one is allowed to change and who decides. `search_rooms` (Data) can only read, so the agent may call it freely and repeatedly; it has a read-only annotation and needs no approval. `book_room` (Action) changes exactly one thing, one booking for the signed-in student, and assumes the decision has already been made: the user named the room. `plan_study_session` (Orchestration) exists for the case where the user delegates the decision ("anything between 4 and 6"), and its only job is the policy that connects the other two: scan half-hour starts, take the earliest slot with a free room, prefer the tightest fit, and retry the next room if one is taken in between. I kept the policy out of the Action tool so `book_room` stays predictable, and I made the orchestrator call the same service functions the other two tools wrap, so the three can never disagree about availability. Several things I first wanted as arguments became structural decisions instead. The booking holder comes from the transport (an environment variable the host sets), not from a model-chosen argument, so the agent cannot book in someone else's name. Every side-effecting call needs human approval in the host. The host also pins a hash of each tool's definition and refuses to start if it changes, which addresses the description-poisoning weakness I criticised in the Fetch server.

Three tools felt right for this use case, but only because each is narrow. A real assistant would need `cancel_booking` and `list_my_bookings` almost immediately; I exposed the latter's read path as a resource (`studyspot://bookings/{id}`) to stay within the brief. The hardest part was failure design: about half the test suite is predictable errors (past dates, closing time, quota, races, injected text), each with a stable code and a hint the model can act on. Next steps: add cancellation as a fourth, approval-gated Action tool; replace the demo dataset with the library's real reservation API behind the same interface; move to streamable HTTP with OAuth so identity comes from a real login; and add an LLM-based classifier alongside the pattern-based injection filter, which is a heuristic rather than a guarantee.
